# A mocked renderer can only prove the input order, not the rendered one

**Date:** 2026-09-13
**Issue:** #1570 (PR #1573) · **Related:** the FullYearRankingChart mocking pattern

## What happened

`RaceChart` was rebuilt as a stacked `AreaChart` whose bands must read
Distinguished, Select, President's, Smedley from the bottom up. Its spec
mocked recharts — the repo's established pattern — and asserted:

```ts
expect(areas.map(a => a.getAttribute('data-key'))).toEqual([
  'Distinguished', 'Select', 'President',
])
```

Green. The preview shipped with the legend reading **Distinguished,
President's, Select, Smedley** over correctly painted bands. The operator
found it in the browser; the suite could not have.

The assertion was true and useless: it checked the order of the `<Area>`
children **going in**. The legend is generated by recharts from its own
chart store, and for a stacked `AreaChart` that order is not the children's.
Every element between the input and the pixels was mocked away.

The follow-up mattered too. The obvious fix — pass `payload` to `<Legend>` —
**also did nothing**: recharts 3's `Legend` reads `useLegendPayload()` and
ignores the prop entirely. Only because the new test rendered the real
library did that show up as a still-red run instead of a second shipped bug.
The working hook is a `content` function, which lets you keep
`DefaultLegendContent`'s markup and replace only the payload.

## The principle

Mocking a rendering library converts a test of **what the reader sees** into
a test of **what you passed in**. That is the right trade for a data
contract — which series, which values, which dates — because you wrote that
mapping and the library cannot change it. It is the wrong trade for anything
the library *derives*: legend order and content, axis ticks, stacking order,
tooltip rows, colour assignment. Those are exactly the things a version bump
silently changes.

Split it: mock for the data contract, render for real for the derived
output. Rendering for real in jsdom costs one stub — `ResponsiveContainer`
measures its parent, which jsdom reports as 0×0, so clone the child chart
with fixed `width`/`height` and everything below renders.

A useful trigger question before trusting a green chart spec: **if the
library reordered, relabelled or recoloured its output tomorrow, would any
assertion here go red?** If not, the suite is guarding your inputs and the
browser is guarding your users.

## Corollary

When red→green leaves the assertions *and the selectors* untouched and only
the implementation moves, the test was about behaviour. If closing the bug
required editing what the test expects, it was about implementation — and
the next renderer change will get through the same way.
