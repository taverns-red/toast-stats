# ADR-015: One canonical pipeline — modes as parameters, persisted inputs, run-scoped gates and promotion

- **Status:** Accepted (2026-10-11, Ron)
- **Date:** 2026-10-11
- **Issue:** epic #1760 (migration steps #1758, #1756, #1761, #1762, #1763, #1759 + #1764, #1765, #1766, #1767, #1768; audit follow-ups #1769, #1770, #1771, #1772)
- **Evidence:** the 2026-10-11 pipeline mode-parity audit, kept as [the first comment on epic #1760](https://github.com/taverns-red/toast-stats/issues/1760#issuecomment-6111329404). Its D-n (divergence) and I-n (invariant) labels are cited below.
- **Line references:** `dp.yml:` is `.github/workflows/data-pipeline.yml` and `pd.sh:` is `scripts/pipeline/process-dates.sh`, both at `7244c8e1` (#1755).
- **Supersedes:** [ADR-009](009-full-range-rederive-promote-semantics.md) D2 (seed-from-prod plus whole-prefix additive promote). ADR-009 D1, D3 and D4 are kept.
- **Numbering:** 012–014 are reserved for the accepted, not-yet-written ADRs from the 2026-10-09 combined pipeline plan: ADR-012 = D11 (Item 1490 rules live in analytics-core), ADR-013 = D13 (module boundaries, `scripts/` gated), ADR-014 = D12 (a shared-contracts schema for every CDN payload).
- **Priority order (Ron):** data correctness, then safety to enhance, then efficiency.

## Context

The data pipeline has one well-exercised path (daily) and three hand-assembled re-derivation paths (rebuild, rescrape, rescrape-historical) plus prune and backfill. #1742 (P3-1) unified the per-date _loop_ into `scripts/pipeline/process-dates.sh`, but daily still runs its own inline steps, and the stages that only daily has (Find-A-Club enrichment, snapshot schema validation, prior-year pull in rescrape, upload guard in daily) are where today's defects came from.

The audit found 26 divergences from daily: 2 Critical, 4 High, 9 Medium, 9 Low, 1 intended, 1 record correction. All six correctness invariants fail (I-1 through I-6). The common cause is not any one bug:

1. **Stages are attached to modes, not to data.** FAC enrichment (D-1), schema validation (D-9), prior-year YoY (D-8) and the upload guard (D-20) each exist in some modes and not others, so "re-derive date X" means something different depending on which button was pressed. Prod 2026-09-30 and 2026-10-08 already lost enrichment this way (#1758).
2. **Inputs that are not persisted cannot be re-derived.** Raw FAC JSON lives only on the daily runner (`dp.yml:422`), so every non-daily mode can only produce an unenriched snapshot (D-1, D-10).
3. **"All districts" artifacts are computed from whatever is on the runner.** A `districts=61` rescrape wrote seven artifacts scoped to one district (D-2): rankings zeroed for 93 districts, `global-totals.json` with 161 clubs, `manifest.json` with one district, `competitive-awards.json` with `currentAvgClubSize` 0 for 93 districts. The value gate digests one of the seven.
4. **Stores accept writes from any date in any order.** The awards-history year summary is replaced by whichever date transforms last (D-5); club-trends hands a past date the whole program year (D-4, #1759).
5. **Gates read one file per date; promotion copies four prefixes.** The count and value gates key on `all-districts-rankings.json`; the content gate reads a 2.4 % sample for shape (D-12, D-13). Promotion then rsyncs `v1/`, `snapshots/`, `time-series/`, `config/` wholesale (D-11), so one bad staged date holds every date, and a bad date the gates cannot see ships with the good ones. A 30 % shrink of four analytics files and a 55 % shrink of every district file passed `PASS — all 492 checked` in runs 38152756138 and 38148856619.

ADR-009 chose whole-prefix additive rsync because "the safety logic lives entirely in the two gates" and listed scoped per-date promotion as the fallback. The gates have since been shown to cover one artifact out of roughly fifteen per date. The fallback is now the right choice.

## Decision

### P1. One canonical stage list; modes are parameters

There is one per-date runner, grown from `scripts/pipeline/process-dates.sh`, and daily calls it too. A run is described by parameters, never by a mode-specific copy of the steps:

| Parameter   | Values                                                                                                                | Today's mode it replaces                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| `source`    | `scrape` (live, with the #1669 as-of check) · `raw-gcs` (closing-raw resolution #1608) · `historical-url` (4-segment) | rescrape / rebuild / rescrape-historical  |
| `dates`     | explicit list · `yesterday` · `all-raw` · month-ends of a PY from the closing registry                                | daily / rebuild / rescrape `program_year` |
| `districts` | `discover` (per date, from the date's own all-districts CSV) · explicit list (**hydrated**, see P3)                   | daily discovery / `districts` input       |
| `enrich`    | `fetch` (daily: fetch FAC, persist it, merge) · `persisted` (merge the persisted FAC for that date if any) · `none`   | FAC daily-only gate                       |
| `promote`   | `yes` · `no`                                                                                                          | `skip_promotion`                          |

Every date, in every run, goes through the same ordered stages: resolve source → fetch raw → prev-year pull → transform → closing remap → upload guard → enrich (merge persisted or fresh FAC) → compute → **schema validation** → upload → record in the run manifest (P5). A stage that has no input for a date (no persisted FAC for 2019) is logged and counted, not skipped silently and not fatal.

Eliminates: D-1, D-8, D-9, D-10 (a failed daily fetch falls back to `persisted` for that date and is counted), D-20, D-23, D-24, D-26, I-1.

### P2. Every input the pipeline derives from is persisted in staging

- `raw-fac/<snapshotDate>/district_<id>.json` — the daily FAC fetch output, uploaded before the merge (plain, no `-Z`, internal). A re-derivation of a date merges from it. Historical dates with no FAC are processed unenriched and the completeness gate (P5) knows they have no prod enrichment to regress from.
- `raw-csv/<date>/` stays the source of truth for the transform; its `metadata.json` describes the **date's full district set**, written only when the run had it (P3).
- `district_<id>_reports.json` sidecars are inputs (TI daily reports), not derived; a re-derivation never deletes them. This is already true (`cp`, not `rsync --delete`) and becomes a tested contract.

Eliminates: D-1 (re-derivable), D-10 (daily degrades to the last good FAC rather than to nothing), I-6 for enrichment. Consistent with ADR-010 (enrichment stays merged into the raw rows; the raw FAC is simply kept).

### P3. All-districts artifacts need the whole district set, or they are not written

`all-districts-rankings.json`, snapshot `metadata.json`, `manifest.json`, `competitive-awards.json`, `global-totals.json`, `global-club-race.json`, raw-csv `metadata.json` and `v1/rankings.json` are **date-level** artifacts. A run writes them only when its per-district inputs for that date cover the district set named by the date's own all-districts CSV. Two ways to satisfy that, chosen by `districts`:

- `discover`: the run has everything (today's full modes).
- explicit list: the runner **hydrates** the other districts from staging before the transform and compute — `raw-csv/<date>/district-*/` for the transform's per-district counts, `snapshots/<date>/district_*.json` and `analytics/` for the rollups — so the date-level artifacts are computed from a complete set with the subset re-derived. R2 already demands that every input be synced explicitly; this makes it a contract. If hydration cannot complete (a district missing in both the run and staging), the date-level artifacts are **refused** for that date with a counted reason, never written with defaults.

District discovery is per date, from the date's data, in every source (today only rebuild and historical do this).

Eliminates: D-2 (all seven artifacts), D-7, D-25 (a stale raw directory is not in the date's CSV, so it is ignored), I-2.

### P4. Stores are date-aware

- `DistrictAwardsHistoryStore.upsertYearSummary` accepts a summary only when its `snapshotDate` is ≥ the stored entry's for that program year, so a rebuild of a mid-year past date cannot regress a year-end summary. (Alternative considered: upsert only on year-end closes. Rejected: the current PY's in-progress summary feeds Leadership Excellence "on track" today, #1609.)
- `ClubTrendsStore` preload for a snapshot dated D is filtered to points ≤ D before `computeDistrictAnalytics` (#1759).
- Time-series (upsert by date) and club-race (min on rebuild) already satisfy this; the contract test in P6 pins them.

Eliminates: D-4, D-5, I-3, the store half of I-6.

### P5. A run manifest, and gates scoped to what the run touched

Every run writes `runs/<github_run_id>/written.jsonl` to staging: one line per uploaded object — path, sha256 of the uncompressed bytes, the date it belongs to, the stage that wrote it. The runner appends as it uploads; the manifest steps append their `v1/` and `config/` objects. The manifest is run-scoped and derived; it is not a store (the 2026-10-09 plan's objection to a persistent `promotion-state.json` does not apply).

Gates then answer questions about **the run**, not the bucket:

1. **Content gate** reads every manifest object (a daily writes ~1 100; a full rescrape of one date ~1 100; a historical PY ~13 000 — bounded, no sampling). Shape rules stay as #1715 and adopt the shared-contracts schemas as D12 (ADR-014) lands them.
2. **Per-date completeness gate** (new, `scripts/lib/dateCompletenessGate.ts`): for every date in the manifest, compare the staged date directory with prod's: object count per date, district count in `manifest.json`/`metadata.json`, `global-totals.clubs` and `clubsByCountry.countries`, the key-set of a sampled club record per district (`address`, `coordinates`, `meetingDay`… present in prod ⇒ required in staging unless the run declares `enrich=none` for a date with no persisted FAC). Any regression **holds that date** (D8: hold, not warn) unless `allow_value_changes` is set, mirroring ADR-009 D1.
3. **Value gate** keeps its digest of `all-districts-rankings.json` and adds the same stable digest for `global-totals.json`, `competitive-awards.json` and `manifest.json` (metadata excluded) — the other date-level artifacts D-2 corrupted.
4. **Count gate** is unchanged (it guards `v1/` monotonicity).

Eliminates: D-12, D-13, I-4; detects D-1 and D-2 even if P1–P3 regress.

### P6. Promotion copies exactly the manifest

`Promote staging to production` copies the run manifest's objects (per-date `rsync` of `snapshots/<date>/` restricted to manifest paths, per-object `cp` for stores and `v1/`/`config/`), and only for dates the gates passed. A date held by the completeness gate is excluded; the rest of the run promotes; the held date is named in the promotion-held issue. The whole-prefix rsync (`dp.yml:1957-1970`) is removed. `PROMOTED_PREFIXES` becomes an allow-list the manifest paths must fall under (the prod-write guard from #1755 checks it).

Prune `reconcile_prod` and the `place-reports` prod mirror become manifest-driven promotes of their own (their manifests list the deletes and the sidecars respectively), so there is one prod-write mechanism and the prod-write guard test can prove it.

Eliminates: D-11, D-15, D-16, I-5. Efficiency follows for free: the daily promote stops rsync-listing 272 k objects per prefix.

> **Implementation note (2026-10-17, #1763):** the step is `Promote run manifest to production (#1763)` (`scripts/promote-run-manifest.ts --execute`, per-object server-side `cp`); the whole-prefix rsync step is deleted. Two classes the rsync used to sweep up are routed explicitly until step 9 (#1767): `time-series/` files current in staging but stale in prod are recorded in the next run's manifest (stage `publish-stores-carry`), and report sidecars prod lacks are copied by `[reports] Carry missing report sidecars into prod`.

> **Implementation note (2026-10-20, #1767, prune half):** the prune reconcile no longer writes prod itself. `[prune] Plan prod reconciliation` writes the delete manifest; `[prune] Promote prod reconciliation (#1767)` runs the same promoter with `PROD_DELETES_FILE`, after the content and completeness gates, which copies the regenerated `v1/` + `config/` from the run manifest and then runs `rm -r` on the planned prefixes (only if the indexes promoted). `PROD_RSYNC_EXEMPT` is empty. The reports half is still open: `[reports] Mirror placed datasets into prod` and `[rollup] Mirror the reports rollups into prod (#2012)` copy into prod with their own `gcloud storage cp`, and the carry and education-mirror scripts write prod too; `dataPipelinePruneReconcileManifest.test.ts` pins the two direct steps.

### P7. Dead inputs are retired, not kept for compatibility

- rescrape `program_year` generates month-end dates from `docs/month-end-closing-dates.json` (ADR-011), not the 15th (D-6). The allow-listed inline `node -e` from #1743 goes with it.
- `force` means one thing: re-fetch and re-derive even if cached. Daily passes it through; the other sources already behave as forced.
- Backfill joins the `partial-failure-gate` (D-26) and the shared-step exclusions are made uniform (D-22).

## Harness requirements (P3-2, D10 shim)

The existing shim (`scripts/lib/__tests__/fixtures/gcloud-shim/gcloud`) covers `ls`, `rsync -r`, `cp` with headers/`-Z`/`--custom-metadata`, and `objects list --format=json`, with SDK 583 error texts and the 568-vs-588 download behaviours. To test this ADR it must also cover:

- `storage cat` (manifests, `latest.json` reads), `objects describe --format`, `rm -r` (prune reconcile, incoming cleanup), `ls` with a delimiter (the content gate's sub-prefix listing uses the SDK, so a fake `GateBucket` with the recorded `getFiles` shapes stays the seam there);
- **two buckets** (staging and prod) in one `SHIM_ROOT`, so gates and the scoped promote can be run end to end;
- collector-cli stubs that emit **recorded** output shapes for `scrape`, `transform`, `compute-analytics`, `fetch-find-a-club`, `merge-find-a-club` (the fixtures under `fixtures/process-dates/` cover three today; FAC shapes must be recorded from a real `fetch-find-a-club` output, lesson from #1726);
- a fixture corpus: 3 districts × 2 dates, one date with one district's raw missing (step 2), one date with persisted FAC and one without (step 1), prod copies with 32-key records versus staging 21-key (step 3), a two-layer gzip and a truncated object (#1702 class), a PY-spanning club-trends store (step 6);
- a prod-twin assertion library: "every object in prod-shim after promote has exactly one gzip layer, parses, and equals the staging object's sha256".

## Consequences

**Easier.** "Re-derive date X" means one thing. A subset run is either complete or refused. A held date holds itself. Every promoted object was read by a gate. The harness proves a workflow change on a PR instead of on prod's next daily. Efficiency arrives as a side effect of scoping (no 272 k-object listings per prefix at promote time).

**Harder / cost.** Ten PRs with staging dispatches for steps 5 and 7 (Ron runs them). A false hold is possible when prod legitimately has more per date than a re-derivation can produce — a historical date with FAC in prod (none exist: FAC started 2026-05-15) or a TI consolidation; the override is the existing `allow_value_changes`, recorded loudly. The run manifest is a new file per run under `runs/`; it is derived and never read by a later run, so it is not a store in the #1111 sense, but it needs a retention rule (propose: prune deletes `runs/` older than 90 days). Hydration (P3) downloads the other 93 districts' raw and snapshot files for a subset rescrape — about the cost of a daily's raw pull; acceptable because subset runs are rare and today's alternative is corruption.

**Cost of not doing it.** Every re-derivation of a date since 2026-05-15 strips enrichment, and nothing in the gates sees it (D-1 has already reached prod twice). Any `districts=` dispatch poisons the date's rollups and the value gate catches one artifact of seven. A single bad staged date freezes all promotion (the 2026-10-11 staged-diff review, summarized in #1756, first had to restore staging 10-10 from prod before anything could ship). Each new stage added to daily alone (the FAC pattern) recreates the class. The 2017→now full rerun (ADR-009's purpose) cannot be trusted under these gates because they do not read the files it rewrites.

**Risks.** Step 2's refusal could leave a subset run writing no date-level artifacts at all when staging hydration is unavailable (first run of a date); that is the intended fail-closed state and the summary says why. Step 5 changes the only prod write path; it must ship behind `skip_promotion` proof runs, with the old step deleted only in a separate PR after a promoting run is reviewed. Step 7 touches the daily run; schedule it on a day with no month-end close pending.

## Alternatives considered

- **Keep whole-prefix promotion and widen the value gate to every file.** Rejected: the gate would still be bucket-wide, so a held date still blocks all dates, and it does not solve the parity defects (D-1, D-2) that produce the bad data in the first place.
- **Carry forward prod values on a subset run (#1756's second option).** Rejected: a run's output would depend on prod's previous output, not on inputs; it hides a missing input as a stale value.
- **Only year-end closes update the awards store.** Rejected (see P4).
- **A persistent `promotion-state.json`.** Rejected, as in the 2026-10-09 plan: the run manifest is per run and derived, not accumulated.
- **Make FAC a separate pipeline that enriches prod in place.** Rejected: it would be a second prod writer with its own gates, and ADR-010 settled that enrichment lives in the snapshot rows.
